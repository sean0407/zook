依 `Zook-0.13-開發提示詞` 進行。對話被壓縮後，以這份檔案為準接續。

## 準備工作

- 分支 `stage/7`，從 `item/error-kinds` 開出（錯誤分類集中，併入 0.13.0）。
- 驗收腳本 `scripts/acceptance.py`：用真實 CLI 檢查 20 項。基準存在 `docs/0.13-baseline.json`。
  - 用法：`python3 scripts/acceptance.py --compare docs/0.13-baseline.json`，結束碼 0 表示沒有變差。
- 基準結果：20 項都通過過。
  - 第一次執行 19 項通過；「動作前先問」失敗是檢查寫錯（選到不需核准的 `zook_remember`），改用一定要核准的「建立排程」後通過。
  - 第二次執行時 Antigravity 的額度剛好用完（Gemini 週額度原本只剩約 3%）。這是外部狀況，腳本把額度用完標為「略過」，不算變差。
  - **影響**：額度重置前，Antigravity 的檢查都會被略過。項目 1 需要它的串流實測，到時改用 Antigravity 裡另一組模型的額度來測，測不了就如實記錄。

## 替使用者做的決定

- 驗收腳本的核准檢查用「建立排程」而不是「記住一件事」，因為後者在設計上本來就不需要核准。
- 額度用完視為略過而不是失敗。

## 項目 1：回覆逐字顯示（0.13.0）— 完成

做法：
- `backend/zook/stream.py`：讀各家 CLI 的進度事件，把目前寫到的文字放在記憶體；`GET /api/jobs/<id>/stream` 用事件串流送給視窗；一般查詢工作時也帶 `partial`（手機用）。
- Claude 和 Antigravity 原本就是用串流格式呼叫，只多加了 Claude 的 `--include-partial-messages`。最終結果的讀法完全沒動。
- `frontend/js/37-stream.js`：只重畫正在回覆的那一則；停在底部才跟著捲。
- 開關：設定 →「對話」→「回覆逐字顯示」，預設開。關閉後不記錄片段，Claude 的呼叫參數也回到原本的（有測試）。

完成條件：
- 四家真實 CLI 實測（直接讀事件串流）：Claude 78 次更新、0.9 秒出第一個字；Antigravity 167 次；Grok 15 次（先思考約 44 秒才出字）；Codex 1 次。四家「最後的片段」都和最終回覆完全相同，用量都有。
- 中途失敗換備用模型時片段清空：有測試。
- 先規劃、核准、停止：單元測試與驗收腳本通過。
- Claude 慢慢寫不會被當成沒動靜：有測試。
- 群組兩個成員同時逐字：瀏覽器實測，結尾不閃爍。
- 完整測試 356 項通過；驗收腳本和基準相比沒有變差。

沒做到或沒驗到：
- **Codex 實際上不是逐字**：它的 CLI 只在整則訊息完成時才輸出，所以是整段出現。
- **Grok 會先安靜思考幾十秒**才開始出字，這段時間畫面仍是「正在思考…」。
- Antigravity 用的是它的 Claude 模型實測（Gemini 額度用完）；驗收腳本裡它的三項被略過。
- 片段沒有另外遮蔽金鑰：最終回覆本來也沒有遮蔽，兩者處理一致。提示詞寫的「片段裡的金鑰同樣會被遮蔽」其實是誤會，現況是回覆內文都不遮蔽，只有工具參數會遮蔽。
- iPhone 沒有實機測。手機是輪詢，約每 1.5 秒跳一段。

替使用者做的決定：
- 新訊息開始時，前一則的文字會留在畫面上直到新訊息有第一個字，避免中間空白。
- 串流結束後片段不立刻清掉，等完成的回覆取代它，避免閃一下「正在思考…」。
