## 項目 2：Bot 忙碌時排隊（0.13.1）— 完成

- 重送同一則（相同編號）不會多佔一個位置：有測試。

## 項目 3：只有使用者親自送出的回合能改排程（0.13.1）— 完成

做法：
- 每個工作記下來源 `job['origin']`：沒有這個欄位就是使用者；其他是 `schedule`、`trigger`、`bot`。
- 來源不是使用者時，建立、修改、刪除排程的工具直接拒絕並告訴 Bot 原因，連核准都不問。列出排程仍可用。
- 群組回合的來源看「誰啟動這次討論」：使用者打字是使用者；排程啟動是排程；Bot 用工具啟動是 Bot。
- 不提供關閉的開關。

獨立審查發現與處理（已全部修正並補測試，除非另註）：
1. 「重答」把排程回合洗成使用者回合 → 重答沿用原本的來源。
2. 還原備份會把備份當時排隊中的訊息再送一次 → 還原與損壞復原時都清掉佇列。
3. **既有問題**：手機連線權杖放在環境變數，同一台 Mac 的程式可讀取並冒充已配對手機（送訊息、自己核准）→ 改用管線傳給 `zook-remote`（`--token-stdin`）。實測連得上且 `ps` 看不到。
4. 非使用者回合可寫入所有 Bot 共用的記憶，等於把外部內容帶進之後的使用者回合 → 非使用者回合不能寫共用記憶；寫在自己身上的會標記來源，提示詞裡註明「只當參考」。
5. 新訊息可在兩則回覆之間插隊 → 佇列非空時一律排到後面。
6. 同步刪除對話時沒清佇列 → 已清；對話不存在的排隊訊息直接丟棄，不會落到別的對話。
7. 送出時遇到非預期錯誤會讓佇列永久卡住 → 一律轉成看得到的失敗訊息並繼續下一則。
8. 當機時可能重送一則 → 改成先從佇列取出再送，同一次存檔完成。

這項規則不涵蓋的（設計上的限制，如實記錄）：
- CLI 自己的原生工具可以直接改 Mac 上的檔案（包含 Zook 的資料檔、系統排程），這條規則擋不到。
- 群組或排程對話裡，使用者之後親自輸入訊息，那一回合就是使用者回合，而對話紀錄仍含先前排程或 Bot 的文字。
- 管理員 Bot 在非使用者回合仍可建立 Bot、建立群組、啟動討論（它啟動的討論來源是 Bot，排程工具仍被拒）。
- Bot 沒有可以改金鑰或連接器設定的工具，所以這部分沒有東西要擋。

完成條件：排程回合三種修改都被拒、使用者回合照常要核准、排程啟動的群組討論不算使用者回合：都有測試。完整測試與驗收腳本通過。

替使用者做的決定：
- 群組以「誰啟動討論」判定來源，而不是一律視為非使用者。否則你在群組裡親自要求建立排程的現有功能會壞掉。
- 排程回合仍可寫入自己的記憶（每日摘要這類用途需要），只是會標記。

## 項目 5：對話過長自動壓縮（0.13.2）— 完成

做法：
- `backend/zook/compact.py`。兩種情況會把前面的對話整理成摘要，讓 CLI 從摘要開一個新的工作階段：
  1. CLI 回報「對話太長」（任何一家）：整理後把這一則重試一次。
  2. 連續兩則回覆回報的輸入量都超過門檻（只對不會自己整理的 CLI：Grok、Antigravity、Gemini、自訂）。門檻預設 15 萬 Token，Antigravity 60 萬。
- Claude 和 Codex 會自己整理長對話，所以平時不動它們，只在它們回報太長時才處理。
- 摘要由同一個模型產生（多一次模型呼叫，唯讀）。訊息本身全部保留在畫面和資料檔；畫面在那一則上方畫一條線「前面的對話已整理成摘要，Bot 從這裡接續」。
- 防呆：摘要失敗兩次就停止並在回覆下註明；整理後用量沒有降到七成以下也停止，不會反覆再壓。
- 開關：設定 →「對話」→「對話過長時自動整理」，預設開。關閉後 CLI 回報太長時照實顯示「對話太長」的錯誤（有測試）。

完成條件：
- 假 CLI：連續兩則超過門檻才觸發、摘要只含前面的對話、新的提示詞帶摘要、失敗兩次停止、沒變小就停止、CLI 回報太長時整理並重試成功：都有測試。
- 真實 CLI（Antigravity 的 Claude 模型，把門檻調低到 1000 來觸發）：第三則時產生摘要，第四則要它列出先前說過的代號、預算、交期、負責人，四項都答對。
- 完整測試 376 項通過；驗收腳本和基準相比沒有變差。

沒做到或沒驗到：
- 輸入量是 CLI 回報的整個回合總和，一個回合內多次呼叫模型時會偏高，所以用「連續兩則都超過」來避免誤觸。這是估算，不是精確的上下文大小。
- 沒有用真的超長對話（十幾萬 Token）測過，只用調低門檻的方式觸發。
- 摘要不會同步到其他 Mac（那條分隔線的標記會）。

## 項目 8：Grok 指定資料夾（0.13.3）— 完成

- 查證：新版 Grok 仍不接受額外資料夾（`--add-dir` 在這種執行方式下被拒）。但它的嚴格沙盒會把檔案工具限制在啟動的資料夾內。
- 做法：存取範圍是「指定資料夾」時，Grok 改成從那個資料夾啟動。Zook 給它的設定放在該資料夾的 `.grok`（帶 `.zook-owned` 標記），回覆結束就刪除；上次當機留下的會自動清掉。資料夾裡原本就有 `.grok` 時不執行，不動使用者的東西。
- 真實 Grok 透過 Zook 實測：資料夾內讀檔、寫檔成功；資料夾外讀檔、寫檔都被擋；Zook 工具（記憶）照常可用；結束後 `.grok` 已刪除。另有三項自動測試。
- 限制：這個模式下 Grok 讀不到對話附件（附件放在 Bot 工作區，在資料夾外）。Grok 的嚴格沙盒不限制系統暫存區。主動性是「謹慎」時 Grok 仍只在 Bot 工作區，和原本一樣。
