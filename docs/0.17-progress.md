## 項目 1：任務引擎的骨架（0.17.0）

做法：
- `backend/zook/tasks.py`：資料、提示詞、工具；`backend/zook/taskrun.py`：執行迴圈（混進 App）。前端 `frontend/js/41-tasks.js`。
- 設定 →「任務引擎」開關，預設關閉。開啟後群組的討論方式多「自動（主持人決定）」。關閉時這個選項不出現；用 API 硬送也會照「自由」執行，設定群組成這個方式會被拒絕（有測試）。
- 資料存在 `group['taskRun']`：目標、每項工作（說明、完成條件、負責的成員、狀態、每一次嘗試）、叫醒次數、批次數。
- 主持人的回覆才有 `zook_task_create`、`zook_task_list`、`zook_task_reply`；成員的回覆才有 `zook_task_done`、`zook_task_ask`、`zook_task_blocked`。其他回覆完全沒有這些工具（有測試）。
- 回報工具不收工作編號，綁在那一則回覆上；不是目前這次嘗試、或同一次嘗試再回報，都會被拒（有測試）。沒有回報就結束的嘗試算沒完成。
- 成員只拿到工作說明、完成條件，以及主持人對它提問的回答，看不到群組對話（有測試：使用者訊息裡的祕密字不會出現在成員的提示詞）。
- 每項工作就是一則一般的群組回覆：主動性、存取範圍、核准、來源、共用檔案都沿用。核准卡會寫是哪個工作。
- 執行迴圈由事件喚醒（回報、回覆結束、回答），不詢問 CLI。主持人只在一批都有結果、或有人提問、卡住時被叫醒。
- 上限：同時 4 項、一個目標 12 項、主持人叫醒 8 次、嘗試 30 次。
- 任務板：群組裡一則有 `taskBoard` 的訊息，畫面上是可展開的卡片（狀態、成員、三句回報、產出檔案），收合時顯示「已完成 x／y」。手機顯示同一份文字版（靠左、有底色）。
- Zook 重新啟動時還在進行的工作標「狀態不明」，不自動重做（有測試）；按停止會停掉進行中的工作（有測試）。
- 主持人不能接工作；不能用 Zook 工具的成員（例如 Gemini、自訂 CLI）不能接工作。沒有能接工作的成員、或主持人不能用工具時，這次改用「分工」並在群組說明。

驗收：
- 自動測試 `tests/task_engine_test.py`（7 項）。
- 真實 CLI（`task_bench.py --mode auto`，主持人 Claude、成員 Codex 與 Claude）：三項工作都完成；主持人規劃時就開始派工，Codex 和 Claude 同時工作；批次 1、叫醒 1（相等）；總結卡出現；58.3 秒、5 次模型請求、300,972 token。
- 瀏覽器用那次的真實資料檢查：任務板、成員回覆上的「任務 1」標記、總結卡、設定裡的開關、對話框旁的「自動（主持人決定）」都正常。
- iPhone App 可編譯。

替使用者做的決定：
- 「怎樣算完成」從第一版就必填（交辦在第三版才要求，但沒有它就無法驗收）。
- 主持人規劃到一半就開始派已建立的工作，不等它寫完，節省時間。

## 項目 2：工作之間的先後順序（0.17.1）

做法：
- `zook_task_create` 多一個 `after`：要等的工作編號（只能是已經建立的工作，所以不會繞成一圈）。相依都完成才開始；其中一項沒完成，這項就不開始，標「前面的工作沒有完成」。
- 成員拿到前面工作的三句回報和產出檔名（標明是資料），仍然看不到群組對話。
- 主持人的提示詞說明 `after` 只在真的需要前面的結果時才用，其餘讓它們同時進行。
- 「批次」改成：沒有工作在進行、而且主持人已經知道之前所有結果時開始的一波，才算新的一批（受上限限制而接著開始的不算新批次）。

驗收：
- 自動測試 `tests/task_order_test.py`：A → B、C 獨立時，C 和 A 同時進行，B 在 A 結束後才開始並拿到 A 的回報，C 拿不到；前面失敗時後面不開始；`after` 寫不存在的編號會被拒。
- 真實 CLI（主持人 Claude，成員 Codex 與 Claude）：主持人自己把「依景點寫文案」設成接在「想景點」之後；文案在景點完成的同一秒開始，內容用了工作 1 推薦的景點。批次 1、叫醒 1，36 秒。

## 項目 3：同時進行的上限與派工（0.17.1）

做法：
- 設定 → 任務引擎：「同時進行的工作」1–6 項（預設 4）；每個已安裝、能用 Zook 工具的 CLI 各一個下拉，1–4 項（預設 3），同一個 CLI 的每個帳號各自計算。開關打開才顯示這些下拉。
- 一次最多啟動 2 項，還有可以開始的就 0.3 秒後再看，不會一口氣全部開。
- 主持人指派的成員額度用完或剩不到 10% 時，改派給另一位能接工作、額度足夠的成員（先找同職稱的），並在工具回覆和任務板上寫明「原本交給誰、為什麼、改派給誰」；沒有人可以接時仍交給原本那位並註明。設成「自動選擇」的成員不在派工時檢查額度，由它自己選模型時處理。
- 成員回報後照指示直接結束、沒有再寫文字時，原本會被判成「CLI 沒有回傳內容」而失敗；現在用它的回報當成那則訊息，不算失敗。只限已經用工具回報過的任務回覆（有測試）。

驗收：
- 自動測試：每家上限設 1 時三項依序進行、絕不重疊；設定值超出範圍會被拒；Claude 額度剩 4% 時，交給 Claude 成員的工作改派給 Codex 成員，由 Codex 完成（用假 CLI）。
- 固定題目比較（`docs/0.17-bench-split.json` 對 `docs/0.17-bench-auto.json`）：

| | 時間 | 模型請求 | token |
|---|---|---|---|
| 分工（0.16 以前就有） | 58.2 秒 | 4 | 191,718 |
| 自動（任務引擎） | 48.2 秒 | 5 | 301,508 |

  快了約 17%；多 1 次請求，是主持人收齊回報後整理總結。token 較多：每次請求各家 CLI 都要載入一次工具說明（大多是快取讀取，不是新的輸入），而且同一個題目三次實測落在 218,621 到 306,186 之間，波動比兩者的差距還大。

替使用者做的決定：
- 每家 CLI 預設同時 3 項（不是 2）：設 2 時三位都用 Claude 的群組無法三項同時進行，違反 0.17.0 的驗收。

### 0.17.1 的 Codex 例行審查

- Zook 帳號「Waifdance」、gpt-6.2-sol、medium，約 118,173 token（Codex 預設帳號本週剩 15%，沒有用）。
- 找到 8 項，全部修了：
  - 高：「自動選擇」的成員和換到備用模型的回覆，沒有算進該 CLI 的上限。改成照每項工作實際在用的模型（含備用模型）計算；自動選擇的成員在派工時就從還有空位的 CLI 裡選定模型。換到備用模型那一刻仍可能暫時多一項（已列為限制）。
  - 高：成員回報後 CLI 出錯時，原本會被當成完成，接在後面的工作也會開始。改成這次嘗試算沒完成（附原本的回報），後面的工作不開始（有測試）。沒有回報、只是用了內建工具後沒有文字的回覆，仍然算失敗（有測試）。
  - 中：標題是數字時，`after` 可能指到錯的工作。改成只認工作編號（有測試）。
  - 中：改派可能選到「自動選擇」而實際沒有可用模型的成員。改派只考慮有指定模型的成員。
  - 中：同一位成員有兩項工作時，第二項會佔住一個名額，讓其他成員的工作等著。改成成員忙碌時先讓別的工作開始（有測試）。
  - 中：有人提問、主持人沒回答時，任務會直接結束，主持人沒有收到最後的失敗狀態。改成最後再叫醒主持人一次，交代哪些工作因此停下（有測試）。

  - 低：主持人叫醒次數到上限的那一輪，會把沒開始的工作也算進嘗試次數。改成先決定要不要停，再登記要開始的工作。
